## Codebase Map

### Main files and their roles

- **`app.py`** — Flask application factory (`create_app`). Configures the SQLite DB URI (`DATABASE_URL` env var, defaults to `sqlite:///mixtape.db`), initializes the shared `db` (Flask-SQLAlchemy) instance, registers the four blueprints under their URL prefixes (`/songs`, `/playlists`, `/users`, `/feed`), and calls `db.create_all()` on startup. There is no `/` route, so hitting the bare root URL in a browser returns a 404 by design — this is an API-only app.
- **`models.py`** — All SQLAlchemy models: `User`, `Tag`, `Song`, `ListeningEvent`, `Rating`, `Playlist`, `Notification`, plus three association tables (`friendships` — symmetric many-to-many self-join for friends; `song_tags` — many-to-many between songs and tags; `playlist_entries` — many-to-many between playlists and songs, but with extra columns `position`, `added_by`, `added_at`, so it's a genuine join table, not a bare secondary table). Every model has a `to_dict()` used directly as the JSON response shape — there's no separate serializer layer.
- **`routes/`** — One blueprint per resource area. Every route handler does *only* request parsing (pulling query params / JSON body), calling exactly one service function, and formatting the response (`jsonify` + status code) or catching a `ValueError` and turning it into a 400/404. No business logic lives in the route layer.
  - `routes/songs.py` — search, get one song, rate a song, record a listen.
  - `routes/playlists.py` — create playlist, get playlist metadata, list songs in a playlist, add a song to a playlist.
  - `routes/users.py` — get user, get streak, list/mark-read notifications.
  - `routes/feed.py` — "friends listening now" and general "activity" feed.
- **`services/`** — All business logic. This is where the five known bugs live.
  - `streak_service.py` — `record_listening_event()` creates a `ListeningEvent` and calls `update_listening_streak()`, which compares `today` to the user's `last_listened_at.date()` to decide: same day → no change, exactly one day later → increment, otherwise → reset to 1.
  - `feed_service.py` — `get_friends_listening_now()` finds each friend's most recent `ListeningEvent` within a `RECENT_THRESHOLD` window; `get_activity_feed()` is explicitly *not* recency-filtered (by design — it's a different feature, a full history feed capped at `limit`).
  - `search_service.py` — `search_songs()` does a case-insensitive `ilike` match on title/artist, joined against `song_tags`; `get_song()` fetches one song by ID.
  - `notification_service.py` — `create_notification()` is the single low-level constructor. `add_to_playlist()` calls it (notifying the original sharer when someone else adds their song to a playlist). `rate_song()` saves/updates a `Rating` row but is the one place that does *not* call `create_notification()`.
  - `playlist_service.py` — `create_playlist()`, `get_playlist()` (metadata only), `get_playlist_songs()` (ordered by `playlist_entries.position`), `get_user_playlists()`.
- **`seed_data.py`** — Drops and recreates all tables, then inserts 5 users with pre-established bidirectional friendships, 25 songs (deliberately split into 0-tag / 1-tag / 3+-tag groups to expose Issue #3), 3 playlists, a mix of very recent (~10–20 min old) and older (2–58 hours old) `ListeningEvent` rows to expose Issue #2, pre-set streak values, and one pre-existing "song added to playlist" notification so the *working* notification pattern is visible before touching Issue #4. **Note:** all of `seed_data.py`'s timestamps are relative to `datetime.now(timezone.utc)` *at the moment the script runs* — since they don't update afterward, re-run `python seed_data.py` before testing time-sensitive bugs (streak "today" logic, feed recency) if much wall-clock time has passed since the last seed.

### Data flow — a user shares a song, a friend adds it to a playlist, the sharer gets notified

1. `POST /playlists/<playlist_id>/songs` with `{"song_id": ..., "added_by": ...}` hits `routes/playlists.py::add_song`.
2. The route does input validation only (checks `song_id`/`added_by` are present) and calls `services.notification_service.add_to_playlist(playlist_id, song_id, added_by)`.
3. `add_to_playlist` loads the `Song`, the adding `User`, and the `Playlist` (raising `ValueError` → 400 if any is missing). If the song isn't already in `playlist.songs` (the `playlist_entries` secondary relationship), it appends it and commits.
4. Only then does it check `if song.shared_by != added_by_user_id` — if the person adding the song isn't the person who originally shared it, it calls `create_notification(user_id=song.shared_by, notification_type="song_added_to_playlist", body=f"...")`.
5. `create_notification` is a thin wrapper: builds a `Notification` row and commits.
6. The sharer later calls `GET /users/<id>/notifications`, which hits `routes/users.py::notifications` → `notification_service.get_notifications()`, which queries `Notification` filtered by `user_id` (and `read=False` if `unread_only=true`), ordered newest-first.

This is the **working** pattern that Issue #4 breaks: `rate_song()` in the same file follows the same shape (load song, load rater, save the `Rating`) but never reaches step 4 — it has no `create_notification` call at all, so a song's sharer never finds out someone rated it, even though the exact same "was it someone other than the sharer" check that exists in `add_to_playlist` would apply just as well here.

### Patterns noticed

- **Routes never touch the DB directly except `routes/users.py::get_user`**, which does a bare `db.session.get(User, user_id)` instead of going through a service — everything else in the app funnels through `services/`.
- **Every service function that takes an ID either finds the row or raises `ValueError`**, and every route wraps its service call in `try/except ValueError` → JSON error + appropriate status code. This is consistent enough that a missing `try/except` or a missing `ValueError` raise would stand out immediately when reading a route.
- **All timestamps are UTC-aware in Python (`datetime.now(timezone.utc)`) but SQLite/SQLAlchemy silently stores and returns them as naive datetimes** (verified directly: a `datetime` with `tzinfo=UTC` going into a `db.DateTime` column comes back out with `tzinfo=None`, same wall-clock numbers). Every place in the codebase that re-attaches `tzinfo=timezone.utc` after reading from the DB (e.g. `streak_service.py`'s `last_listened.replace(tzinfo=timezone.utc)`) is doing so because of this, and it's *consistent* — so despite looking suspicious, it doesn't itself cause any of the five bugs.
- **The bugs are all one-line, targeted defects, not structural problems**: a wrong comparison operator/value (`weekday() != 6`, `RECENT_THRESHOLD`), a stray slice (`[:-1]`), an unnecessary join, and one missing function call. None of them require touching more than one function to fix.

## Root Cause Analysis

### Issue #1 — My listening streak keeps resetting

**How I reproduced it**: `tests/test_streaks.py` already contained a test the assignment author wrote for exactly this scenario, `test_streak_increments_on_sunday`, which listens on a Saturday then a Sunday and asserts the streak goes from 1 to 2. Running `pytest tests/test_streaks.py -v` before touching any code showed it failing (`assert 1 == 2`), while the other four streak tests passed. That's a clean reproduction: the failure is isolated to the Sunday case specifically, not the general "consecutive day" case (`test_streak_increments_on_consecutive_day`, which uses a Monday→Tuesday transition, passed fine).

**How I found the root cause**: Opened `services/streak_service.py` and read `update_listening_streak()` top to bottom. The function has three branches keyed off `days_since_last`: 0 (no change), 1 (increment), anything else (reset to 1). Line 73 reads `elif days_since_last == 1 and today.weekday() != 6:` — the moment I saw a weekday check bolted onto what should be a pure day-count comparison, that was the specific line, not just a "suspicious area." I confirmed the mechanism: Python's `datetime.weekday()` returns `0` for Monday through `6` for Sunday, so `today.weekday() != 6` evaluates to `False` precisely when `today` is a Sunday — which routes a legitimate one-day-gap listen straight into the `else` branch (reset to 1) instead of the increment branch, on Sundays only.

**The root cause**: `update_listening_streak()` was supposed to increment the streak whenever exactly one day had passed since the last listen, with no exception for any particular day of the week. Someone added `and today.weekday() != 6` to that condition, which excludes Sunday from ever qualifying for the increment branch (since `weekday() == 6` on Sunday makes `!= 6` false). Any streak-continuing listen that happens to land on a Sunday falls through to the `else: user.listening_streak = 1` branch and gets reset, even though the user listened on consecutive days.

**My fix and side-effect check**: Removed the `and today.weekday() != 6` clause entirely, leaving `elif days_since_last == 1:`. Ran the full `test_streaks.py` file — all 5 tests pass now, including same-day (no double count), skipped-day (still resets), and the Sunday case. Also ran the full `pytest tests/` suite to confirm nothing outside streak logic (search, playlists) was affected by this one-line change. Since the fix only removes a condition (never adds new reset/increment paths), the only behavior that changed is Sunday specifically — verified by keeping all four originally-passing tests green.

### Issue #2 — Friends Listening Now shows people from yesterday

**How I reproduced it**: There's no existing test file for `feed_service.py`, so I wrote a controlled reproduction script directly against an in-memory DB: created a user, one friend, and a single `ListeningEvent` for that friend timestamped `datetime.now(timezone.utc) - timedelta(hours=2)`, then called `get_friends_listening_now()`. Against the original code, that friend showed up in the result even though they listened 2 hours ago — clearly not "now" by any reasonable definition. I avoided relying on `seed_data.py`'s built-in "older events" purely from reading them, because those timestamps are computed once relative to when the script runs and decay as real time passes during a long investigation session (I confirmed this happened — by the time I got back to testing against the seeded DB, events that were "10 minutes old" at seed time were 40+ minutes old in wall-clock time).

**How I found the root cause**: My first hypothesis, before writing any fix, was a timezone bug: SQLite stores/returns naive datetimes (I confirmed this directly — a `datetime` created with `tzinfo=UTC` comes back from a round trip through the DB with `tzinfo=None`), so I suspected the aware `cutoff` value being compared against naive stored values might silently misbehave. I tested this directly by compiling the actual SQL SQLAlchemy generates for the filter (`query.statement.compile(..., compile_kwargs={"literal_binds": True})`) and by testing exact boundaries with synthetic events at 23 hours (should be included) and 25 hours (should be excluded) relative to `now`. Both boundaries worked exactly as expected — the naive/aware theory was a dead end; SQLAlchemy's SQLite dialect strips `tzinfo` consistently on both the write and the comparison side, so the arithmetic itself is correct. That ruled out the comparison logic, which pointed me back to the one remaining suspect: the *value* of `RECENT_THRESHOLD` itself (`timedelta(hours=24)`, defined at the top of `feed_service.py`). Re-reading `seed_data.py`'s own comments — "Recent events (within the past 30 minutes) — should appear" vs. "Older events... should NOT appear... after fix" for events starting at just 2 hours old — confirmed the intended window was much narrower than 24 hours.

**The root cause**: `RECENT_THRESHOLD = timedelta(hours=24)` is not a comparison bug — the `>=` cutoff filter itself works correctly at whatever threshold it's given. The bug is that 24 hours is simply the wrong threshold for a feature called "Friends Listening Now," which is supposed to represent live/current activity. With a 24-hour window, any friend who listened at any point in the last full day — including "yesterday evening" from the perspective of someone checking the app the next morning — qualifies as "listening now," which is exactly the reported symptom.

**My fix and side-effect check**: Changed `RECENT_THRESHOLD` from `timedelta(hours=24)` to `timedelta(minutes=30)`, matching the "within the past 30 minutes" window `seed_data.py`'s comments describe as the intended "recent" cohort. Reran my synthetic 2-hour-old-friend script — the friend no longer appears — and added a second synthetic case (a friend with both a 10-minute-old and a 2-hour-old event) confirming the recent one still surfaces correctly. I explicitly checked `get_activity_feed()` (the other function in the same file) was untouched, since its docstring says it's intentionally *not* recency-filtered — a different feature — and reran it live against freshly reseeded data to confirm it still returns full history regardless of age, while `listening-now` now only returns the genuinely-recent subset.

### Issue #3 — The same song keeps showing up twice in search

**How I reproduced it**: `tests/test_search.py` already has `test_search_no_duplicates_multi_tag_song`, written for exactly this bug, with a comment noting "Should be 1, bug causes it to be 3." Running it before any fix showed it **passing** — no duplication. I also hit the live app directly (`curl "http://127.0.0.1:5000/songs/search?q=Crown%20Heights"` against the real seeded 3-tag song "Crown Heights Anthem") and got `count: 1`, no duplicates either. So the reported HTTP-visible symptom genuinely does not reproduce in this environment as literally written — I want to be honest about that rather than claim a reproduction I didn't get.

**How I found the root cause anyway**: Reading `search_service.py`, `search_songs()` does `db.session.query(Song).outerjoin(song_tags, Song.id == song_tags.c.song_id).filter(...)` — an outer join to the tag association table whose columns are never referenced anywhere in the filter or the returned data. A join that doesn't constrain or select anything but *does* have a one-to-many relationship on the join key (one song, multiple tag rows) is the textbook shape of a row-fanout bug, so I verified it directly at the SQL level rather than trusting the passing test: I ran the same join as a raw SQLAlchemy Core query (`db.session.execute(select(Song).outerjoin(song_tags, ...)).scalars().all()`, the modern 2.0-style execution path) against a 3-tag song, and got **3 rows back** — confirmed the join really does fan out at the database level. Then I ran the *exact* code as written (`db.session.query(Song)...all()`, the legacy Query API used in `search_service.py`) against the same data and got **1 row**. That contrast — same join, same data, different result depending on which SQLAlchemy execution API is used — is what pinned down the actual mechanism: the legacy `Query` API in the currently-installed SQLAlchemy version (2.0.51) automatically deduplicates full ORM-entity results by identity, silently absorbing the fanout that the raw join produces. That's an incidental behavior of the ORM layer, not a fix for the underlying join.

**The root cause**: The `outerjoin(song_tags, ...)` in `search_songs()` serves no purpose — it doesn't filter on tags and none of `song_tags`'s columns are selected — but it does cause the query to return one row per matching `song_tags` entry rather than one row per song, so a song with 3 tags produces 3 duplicate rows in the raw SQL result set. This bug is real and latent, it's just currently masked because the legacy `Query.all()` API happens to deduplicate entity-level results before they reach `to_dict()`. If this code were ever migrated to the 2.0-style `select()`/`session.execute()` API (which SQLAlchemy's own docs describe as the forward-looking direction), the duplicates would start appearing over HTTP with no other code change required — that's exactly the kind of bug that should be fixed even though it isn't currently visible.

**My fix and side-effect check**: Removed the `outerjoin` entirely (and the now-unused `Tag`/`song_tags` imports) since it wasn't doing any filtering work. Re-verified with the same raw 2.0-style `select()` check used to diagnose the bug — now returns exactly 1 row for the 3-tag song, confirming the fix holds even under the execution path that doesn't benefit from the ORM's auto-dedup. Confirmed tags still appear correctly in the response (`"tags": ["rap", "hip-hop", "boom bap"]`) since they're loaded independently through the `Song.tags` relationship (`lazy="subquery"`) inside `to_dict()`, which this change doesn't touch. Ran the full test suite (all 13 tests, including the pre-existing single-tag/no-tag/no-match search cases) and hit the live search endpoint again to confirm no regressions.

### Issue #4 — I got notified when a friend added my song to a playlist but not when they rated it

**How I reproduced it**: Found a song ("Block Party") shared by `darius` in the seeded data, then had a different user (`nova`) rate it via `POST /songs/<id>/rate`. The request succeeded (201, a `Rating` object came back), but `GET /users/<darius_id>/notifications` before and after the rating both returned `{"count": 0, "notifications": []}` — no notification was ever created for darius, the song's original sharer.

**How I found the root cause**: The README explicitly calls out the working call chain for playlist adds (`add_to_playlist()` in `notification_service.py`), so I read that function first as the "known good" pattern: it loads the song/adder/playlist, does the actual playlist-add work, then — as a distinct final step — checks `if song.shared_by != added_by_user_id` and calls `create_notification(...)` if so. I then read `rate_song()` in the same file line by line, function to function, the way the assignment recommends (top-down, not "jump to where you think the bug is"). `rate_song()` loads the song and rater, upserts the `Rating`, commits, and returns — there is no notification-related code at all after the commit. The moment that confirmed it wasn't just "notification logic is buggy somewhere" but specifically "the call is entirely missing" was diffing the two functions' shapes side by side: both have the identical "is the actor someone other than the sharer" check available (`song.shared_by` vs. the acting user's ID) since both already load `song` and the acting user, but only `add_to_playlist()` ever reaches a `create_notification()` call.

**The root cause**: `rate_song()` never calls `create_notification()` under any circumstance. This isn't a bug in a comparison or a boundary condition — it's an entire step missing from the function, architecturally identical to the step that's present and working in `add_to_playlist()`. The song's original sharer has no way of ever discovering someone rated their song.

**My fix and side-effect check**: Added a `create_notification(user_id=song.shared_by, notification_type="song_rated", body=f"{rater.username} rated your song '{song.title}' {score}/5.")` call after the rating commit, guarded by the same `if song.shared_by != user_id` check `add_to_playlist()` uses, so self-ratings don't generate a self-notification. Verified live: rating a friend's song now produces exactly one `song_rated` notification for the sharer with the expected body text; rating your own song produces zero notifications (checked nova's own notification list stayed at just her pre-existing "song added to playlist" notification, unchanged). Also wrote `tests/test_notifications.py` (no test file existed for this service before), confirmed it fails against the pre-fix code (temporarily swapped the old file back in and reran — got `assert 0 == 1`) and passes against the fix, then ran the full suite (15 tests) to confirm no other functionality regressed.

### Issue #5 — The last song in a playlist never shows up

**How I reproduced it**: `tests/test_playlists.py` already had two tests written for this — `test_playlist_returns_all_songs` (asserts a 5-song playlist returns `len(songs) == 5`, with the comment "Bug causes this to return 4") and `test_playlist_returns_songs_in_order` (asserts the returned titles are `Track 1`...`Track 5`). Running `pytest tests/test_playlists.py -v` before any fix showed both failing — the first got 4 songs instead of 5, the second was missing `Track 5` specifically (not a random song — always the last one). I also hit the live app: `GET /playlists/<id>/songs` on a real seeded 7-song playlist returned only 6 songs, missing the last one by position ("Free Throws").

**How I found the root cause**: Opened `services/playlist_service.py` and read `get_playlist_songs()`. It builds `songs` via a query joined to `playlist_entries`, ordered ascending by `position` — that part is correct and matches the docstring. The very next and final line is `return [song.to_dict() for song in songs[:-1]]`. The `[:-1]` slice was the specific cause the moment I saw it: it's a plain Python list slice that drops the last element of whatever `songs` is, regardless of playlist size or which song happens to be last — consistent with the test failure always dropping `Track 5` (the last position) rather than any particular song by identity.

**The root cause**: After correctly querying and ordering all songs in the playlist, the return statement slices the result with `songs[:-1]`, which unconditionally discards the last song in the (correctly-ordered) list before converting to dicts. There's no conditional logic here — it always drops exactly one song, whichever is currently in the last position, on every call regardless of playlist length.

**My fix and side-effect check**: Changed `songs[:-1]` to `songs`, returning the full ordered list. Reran `pytest tests/test_playlists.py` — both previously-failing tests pass, including `test_empty_playlist_returns_empty_list` (which was already passing and needed to stay that way, since an empty list sliced with `[:-1]` is still `[]`, so that edge case was never actually exercising the bug — worth confirming it doesn't regress with the fix, which it doesn't, since `[][:-1]` and `[]` are equivalent). Verified live against a real seeded playlist: all 7 songs now return, in the correct position order, ending with the previously-missing "Free Throws." Ran the full test suite (13 tests at that point) to confirm the playlist-only change didn't affect streaks or search.
